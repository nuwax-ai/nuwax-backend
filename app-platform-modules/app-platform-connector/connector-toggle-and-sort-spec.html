01

需求原文与解读Requirement

需求一：用户连接维度的启停

用户虽然连接了，但是可以不启用，连接器还是看得到 —— 用户原话，场景定义

背景问题（v1.0 之前）：connector_connection.status 只有 active/expired/error/disconnected 四个值，且全部由系统写入（建连置 active、refresh 失败置 expired）；用户侧只有 DELETE —— 断开即删凭证行 + 删连接行。

也就是说「连接了、但暂时不想让它生效」没有任何手段：要么留着生效，要么删掉、下次用还得重新授权。能启停的只有连接器与动作两级，都要求空间管理员权限，作用于目录条目而非用户自己那条连接。

要做成什么

  • 停用 ≠ 删除：停用后 凭证保留、连接仍在「我的连接」列表、连接器在目录里仍显示「已连接」。
  • 停用后不再被执行解析选中 —— 调该连接器的动作会被明确拒绝。
  • 随时可启用回来，不必重新走一遍授权。

需求二：列表排序优化

排序优化，已连接的排在前面，已连接且启用的排在最前面 —— 用户原话

v1.0 解读为三档。v3.0 起细化为四档（见需求四与 D9）：档 0/1 拆开，是为了让「我启用了、但凭证已过期」的连接器排在未连接之前、却不占住首位。

作用于连接器目录列表（排序为接口固定行为，不接受排序参数）：

档位含义判定档内顺序
0可用存在 enabled=1 且 status='active' 的连接sort_order, id
1已启用但凭证异常（过期 / 出错）存在 enabled=1 的连接，但不满足档 0sort_order, id
2已连接未启用存在连接行，但不满足档 1sort_order, id
3未连接以上皆不成立sort_order, id

档内回落到原有的目录权重 sort_order, id，因此未连接那一大档的顺序与改动前逐条一致 —— 这是验收时最容易查、也最该查的一点。

档 2/3 的判据是「连接行存在」，与目录侧 connected 标签同源（v1.0 用的是 status <> 'disconnected'；现在 disconnected 已是不再写入的历史兼容值，直接用行存在更直白，两者在现有数据上等价）。

实现上不需要写 NOT EXISTS：三个 EXISTS 子查询级联 DESC，三个布尔位恰好切出四种组合（见 D9）。

需求三：把「用户是否连接」与「是否启用」分开

把用户是否连接 与 是否启用状态分开，不然太乱了 —— 用户原话，v2.0 的需求

v1.0 用 status='disabled' 表达「用户停用」。但 status 这一列在 v1.0 之前就已经承载着凭证健康度（active/expired/error），两者是正交的两件事，硬塞进一列就出现两个真实缺陷：

  • 表达不了「我停用了一条已经过期的连接」：写成 disabled 就把 expired 覆盖了，用户下次启用时看不出这凭证其实已经死了。
  • 系统流程会静默改写用户的决定：markExpired() 无条件写 expired、token 刷新成功无条件写 active —— 「停用」不过是这两个值之一，会被覆盖掉。停用过的连接被刷新碰到就自己「复活」了。

所以 v2.0 把用户开关拆成独立列 enabled：status 只保留凭证健康度（系统写），enabled 只表达用户意图（用户写）。两个字段各归其位后，上面两个缺陷不靠加守卫、靠结构本身就消失了。

需求四：连接器查询统一收敛到一个接口　v3.0

/api/connector/providers 统一用这个接口
1. 查询所有官方的连接器　2. 查询所有空间的连接器　3. 查询指定空间的连接器
4. 查询我自己已经启用的连接器
5. 所有查询结果都要标注出来当前用户是否连接和是否启用
6. 当前用户已启用和已连接的排训前面 —— 用户原话，v3.0 的需求（「排训」= 排序）

六条里 1/2/3 是既有能力（v2.0 之前就已支持），本次未改动；4/5/6 是新做的。用一个接口承载全部形态，不给 /connections 加同类过滤参数：

#查询形态怎么调本次
1所有官方的连接器?scope=official已有
2所有空间（我有权限的）的连接器不传 spaceId已有
3指定空间的连接器?spaceId=57（或 scope=space）已有
4我自己已启用的连接器?connectionEnabled=true新增
5标注「是否连接」「是否启用」响应里的 connected / connectionEnabled新增
6已启用和已连接的排前面四档排序（服务端固定）三档→四档

「已启用」的口径由用户拍板：严格只看用户开关 enabled=1，不掺 status。因此「启用了但凭证已过期」的连接器算已启用——查询时它在结果里，真去执行才报 connection_expired。这与 3.3 的「可用」是两个不同的问题，别混。

接口契约API Contract

2.1 新增：启用 / 停用连接

方法 / 路径POST /api/connector/connections/{id}/status
参数id 路径参数（连接 ID）
enabled query，缺省 true，取值 true/false
鉴权登录态；服务端按 user_id 校验归属，非本人一律视为不存在
返回ReqResult<ConnectionDto>（含 enabled / status / profile / providerService / modified 等）
写入范围只写 enabled 一列。不碰 status —— 那是凭证健康度，由系统写。这是 v2.0 与 v1.0 的关键差别：v1.0 这个接口会写 status='disabled'。
幂等重复 disable → enabled 仍为 false、status 原样不动；重复 enable → enabled 仍为 true、status 同样不动
负路径connection_not_found

回 ConnectionDto 而不是 Void：连接控制器其它写接口都回 DTO，且 enabled 与 status 两个字段共同决定这条连接现在能不能用，回传让调用方一次拿全，不必再查一次。

接口路径与参数一个字没改

仍是 POST /connections/{id}/status?enabled=。调用方（含技能脚本 connector.py set-connection-status）无需改动，只是返回体里多了一个 enabled 字段、且 status 不再被这个接口改写。

验收时请一并核对：模块内的调试控制台「没有」启停开关

这是有意的，不是漏做。启停是连接维度的操作（一条连接一个开关），而目录卡片是 provider 维度（一个连接器底下可能有多条连接，见 3.3）。能力中心已定调「悬停展示 连接/断开 按钮，不展示开关」，因此本次不碰前端。

2.2 排序与标注：复用既有列表接口，无新增接口

接口说明本次变化
GET /api/connector/providers目录列表（分页）排序固定为四档；每条新增 connectionEnabled 标注；新增 ?connectionEnabled= 过滤
GET /api/connector/providers/overview总览全量（不分页，前端分组用）排序与标注同上，与 /providers 顺序保持一致；无过滤参数
GET /api/connector/providers/{service}详情 + 动作列表同样补 connectionEnabled 标注

三个接口都不接受排序参数。需要别的排序口径时由客户端自行二次排序。

2.3 新增过滤参数 connectionEnabled　v3.0

参数取值含义
connectionEnabledtrue只看我启用了的连接器（需求 4）——注意含「启用了但凭证过期」的
connectionEnabledfalse只看我没启用的（含未连接 + 连了但停用）
connectionEnabled不传不过滤（行为与改动前一致，向后兼容）

与既有 connected 参数可组合：?connected=connected&connectionEnabled=false = 我连了但停用的。两者互不替代——connected 问「有没有连接行」，connectionEnabled 问「用户开没开」。

验收时注意：参数必须是「包装类型」才能分辨「没传」

服务端用 Boolean（对象）而不是 boolean（基本类型）接收：boolean 分不出「没传」和「传了 false」，而这两者语义正好相反（不过滤 vs 只看没启用的）。同理，若在未部署该改动的实例上打 ?connectionEnabled=true，Spring 会静默忽略这个未声明的参数并返回全量——别把这个当成「过滤生效但没数据」，先确认实例版本。

03

状态语义Status Semantics

3.1 「已连接」「启用」「凭证健康」在代码里是五个不同的概念

这是最容易在验收时搞混的地方，先钉死口径。前三个是库里真实存在的字段，后两个（connected / connectionEnabled）是接口响应上派生出来的标注 —— 它们不新存数据，只是把前三个字段按用户维度聚合后答一个「是/否」问题：

概念落在哪个字段取值谁控制
目录条目是否启用 connector_provider.status enabled / disabled 空间管理员（POST /providers/{service}/status）
我这条连接：用户要不要用 connector_connection.enabled 1 / 0（true / false） 用户本人（POST /connections/{id}/status）
建连时置 1
我这条连接：凭证还能不能用 connector_connection.status active / expired / error 系统（建连、token 刷新、验活）
用户碰不到
我有没有这个连接器的连接 ProviderDto.connected true / false（派生） 无（由连接行是否存在派生，不看 enabled/status）
我启用了没v3.0 ProviderDto.connectionEnabled true / false（派生） 无（由连接行 enabled=1 派生，不看 status）

命名陷阱（三个）

① ProviderDto.status 指的是目录条目的启停（第一行），不是「我的连接」的启停。两者名字相近但语义无关，reviewer 容易看错。

② connector_connection 上也有一个叫 status 的列，但它在 v2.0 里只表示凭证健康度，不再表示用户启停。判断「用户启用了没有」要看 enabled。v1.0 里 status='disabled' 表示用户停用，这个值已随 v2.0 移除。

③ 新的响应字段叫 connectionEnabled 而不是 enabled：ProviderDto 里已有 status 表示目录条目启停，再叫 enabled 会和它看混。connection 前缀点明它属于「我的连接」这一维度（见 D10）。

3.2 connector_connection 上的两个字段，各管一件事

① enabled —— 用户开关（v2.0 新增列）

值含义写入方列表可见 / connected参与执行解析
1 / true用户启用（默认，建连即为真）用户；建连流程可见，true是（还须 status=active）
0 / false用户主动停用用户本人可见，仍 true否

DDL：enabled tinyint(1) NOT NULL DEFAULT 1，通过 ALTER TABLE … ADD COLUMN … AFTER status 增加。DEFAULT 1 让全部存量连接自动视为「启用」，与改动前行为逐字节一致。

② status —— 凭证健康度（语义收窄，不再有用户意图）

值含义写入方列表可见 / connected参与执行解析
active凭证正常建连 / token 刷新成功可见，true是（还须 enabled=1）
expired凭证过期（OAuth refresh 失败）系统可见，true否
error验活 / 执行出错系统可见，true否
disconnected历史兼容值（实际断开由 DELETE 行承担，代码不再写入此值）—查不到否

枚举 ConnectionStatusEnum 里的 DISABLED 已删除；DISCONNECTED 保留但标注为历史兼容值（listByUser/countByProvider 仍有防御性 ne 条件）。

3.3 可用性 = 两个字段同时成立（正交，不是二选一）

这是 v2.0 最该被验收的一点。enabled 与 status 互不覆盖，四种组合各自成立：

enabledstatus能执行吗执行时的错误码
1active能—
1expired / error不能connection_expired
0active不能connection_disabled
0expired / error不能connection_disabled

最后一行是判断顺序的体现：先判 enabled、再判 status。既停用又过期时报 connection_disabled —— 先解决用户意图（去启用），启用后自然会看到 connection_expired（去重新授权）。顺序反了会让用户在「去授权」和「去启用」之间来回跑。

终于能表达「我停用了一条已经过期的连接」

第 3、4 行两种组合里都能看到：停用不会把 expired 抹成别的值，启用也不会把它「治」成 active。下次启用时 UI 上仍能看到 expired，用户就知道该去重新授权 —— 而不是被一句「启用成功」骗着去撞一个已经死掉的 token。

v3.0 提醒：「可用」≠ connectionEnabled

本节的「可用」是第 1 行（enabled=1 且 status='active'）；而接口标注 connectionEnabled 只回答「用户开没开」，第 1、2 两行都是 true。两者不是一回事：connectionEnabled=true 只保证「用户想用」，不保证「现在能用」。排序档 0 / 档 1 的拆分正是这个差别的落地（见 D9）。

3.4 为什么「已连接」是 provider 级、而「可用」是 connection 级

因为一个 provider 底下可以有多条连接，是 N : 1。该项目里就真实存在：ably_control 有 2 条连接。所以「这个连接器启用了没有」在 provider 粒度上不是一个事实，而是一个策略（当前策略：任一连接满足 enabled=1 且 status='active' 即算可用）。

v3.0 的两个标注沿用同一套「任一连接满足即算」的聚合口径：connected = 任一连接行存在；connectionEnabled = 任一连接行 enabled=1。三处口径同源，不会互相打架。

04

关键设计决策Design Decisions · 验收人重点看这里

下面 11 条是本次实现里有取舍、可能引起争议的地方。每条都写了理由和代价 —— 如果验收时认为某条取舍不对，直接在这条下面提，改起来都是局部的。D1 是 v2.0 的核心，D2 是 v1.0 到 v2.0 行为变动最明显的一条；D9–D11 是 v3.0 新增。

D1 · 把「用户开关」从 status 里拆出来，独立成 enabled 列 v2.0 核心

为什么「用户启不启用」与「凭证健不健康」是正交的两件事：前者的写者是用户，后者的写者是系统。挤在一列时值域互斥，就必然有二选一的丢失。拆开之后，两个真实缺陷不靠加守卫、靠结构本身就消失了：

① ConnectorOAuthServiceImpl.markExpired() 无条件写 expired、refresh 成功分支无条件写 active —— 以前这两个流程会静默抹掉用户的停用决定（停用过的连接被刷新碰到就自己「复活」）。现在它们只写 status，碰不到 enabled，这两个方法的代码一行都没改，行为却自动正确了。

② 「我停用了一条已经过期的连接」以前表达不出来（disabled 覆盖 expired）；现在两个字段各存一份，两种事实同时保留。

代价 一次 DDL（ADD COLUMN）。已用 DEFAULT 1 兜住兼容性：存量行全部视为「启用」，与改动前行为逐字节一致；回滚只需 DROP COLUMN。另外判断「可用」从看一个字段变成看两个（见 3.3 的矩阵），调用方要知道这个口径。

D2 · 启用/停用不再改写 status（v1.0 行为已废止）

为什么v1.0 里「启用」会把 status 置成 active，即使这条连接的 token 其实早就死了 —— 等于谎报凭证健康，用户要撞一次墙才发现。v2.0 把这个接口收窄成只写 enabled 一列：启用一条 expired 的连接，它仍然是 expired，执行直接报 connection_expired，提示去重新授权。

代价的另一面是：status 现在只有系统会写，「这条凭证还行不行」这个判断永远来自真实调用（ensureFreshOAuthToken 刷新、验活、执行），不再有人工的乐观写入。

代价 用户点「启用」后如果凭证确实过期，不会得到「成功」的错觉，而是立刻看到 connection_expired。这是刻意的：宁可当场说清，也不要先给个假绿灯。

D3 · 两个错误码各指一条明路：connection_disabled / connection_expired

为什么三种落空指向的解法完全不同：connection_required → 去连接；connection_disabled → 去启用；connection_expired → 去重新授权。混用会把用户引到错的方向 —— 重连只会多出一条连接，原来那条还停着；而给一条停用的连接点「重新授权」也是白费。

connection_expired 这个错误码本来就存在，但在本次之前全仓没有任何地方抛出它（死码）。用户拿着过期连接执行，收到的却是误导性的「请先建立连接」。本次是它第一次真正接线。

代价 执行侧落空时要能区分三种情况，因此 firstBlocked 的判据从「status='disabled'」扩展成「enabled=0 或 status<>'active'」，再在 Java 里按 enabled 优先分类。

D4 · 执行侧挡两处，缺一不可

为什么①显式 connectionId 分支原先完全不看 status —— 不补这一处，调用方传一个连接 ID 就能静默绕过用户的停用决定，「启用/停用」就成了一句空话。②自动解析分支：firstExecutable（v1.0 叫 firstActive，本次改名并加固条件）已同时固定 enabled=1 与 status='active'，停用与过期都天然被过滤；但落空后要能区分「没建过」「建了但停用」「建了但凭证坏了」，否则会报误导性的「请先建立连接」。

代价 连带效果：verifyConnection（内部用显式 connectionId 执行）对停用连接会失败。这是预期行为 —— 停用的连接不该被验活。
另一处代价：两处判断都写成「先 enabled 后 status」的固定顺序，顺序反了会让用户在「去授权」和「去启用」之间来回跑（见 3.3 末行）。

D5 · 排序必须落在 SQL，且不能用 ? 占位符

为什么①/providers 是分页的，在 Java 里补排序太晚 —— 某一页可能整页一条已连接的都没有，正确的行根本不在这一页。②只内联 Long（tenantId/userId，取自登录态而非请求参数，Long.toString() 不含引号、无注入面）而不用 ?：分页的 count 语句会剥掉 ORDER BY，占位符会与参数绑定表错位。

代价 表达式写进了 .last("ORDER BY …")（lambda wrapper 的排序方法只认 SFunction，表达不了子查询），并因此不能再调用 orderByAsc（否则会拼出两个 ORDER BY）。验收时请重点核对分页 total 是否正确。

D6 · 排序档 2 的判据是「连接行存在」，不是某个 status 值

为什么要与目录侧「已连接」标签同源：目录侧的 connected 问的就是「有没有建过连接」（listByUser，停用的也算）。档 2 直接用「行存在」，与这个标签不可能互相矛盾 —— 不会出现「标签说已连接、排序说没连接」。

v1.0 用的是 cc.status <> 'disconnected'。改用行存在后，enabled=0 的连接自然落入档 2，符合「已连接但不可执行」的定义。两者在现有数据上等价：disconnected 已是历史兼容值、代码不再写入。v3.0 起 status 为 expired/error 但 enabled=1 的连接前移到档 1（v2.0 时它们同在「已连接」这一档，见 D9）。

代价 档 2 是「存在连接行、但用户没启用」的集合，语义比 v2.0 收窄了一点（凭证异常的那部分被 D9 提到档 1）。

D7 · 前端一行没改，靠后端排好 + 前端稳定排序

为什么控制台 app.js 的 tabBaseList 按 connected 分组，用的是 JS 的稳定排序，档内会原样保留后端顺序。所以后端排好后，4 个 tab（全部/我的/官方/已连接）的顺序自动都对了，不需要动前端。

代价 这个「隐式依赖稳定排序」比较隐蔽，已写进仓库记忆；若日后前端改成显式排序，需同步。
v2.0 额外收益：前端只用 p.connected，而「已连接」的语义（行存在）本次没变，所以拆列对前端完全透明。

D8 · 两个同名不同义的 connected 各自正名

为什么改动前 SDK 侧 ConnectorApiServiceImpl 有个私有方法叫 connectedServices，判据是 status='active'（问「能不能跑」）；而目录侧 ConnectorCatalogController.servicesOfUser 的 connected 判据是 listByUser（问「建过没有」）。同名不同义，是「乱」的第三个来源，读代码的人极易看错。本次把 SDK 侧那个改名为 executableServices，名字直接说出判据。

代价 SDK 对外方法 hasActiveConnection 不改名（它是对外契约，改名会扩散出 connector 模块，违反「改动不扩散」的约束），只把内部实现换成 firstExecutable。所以那个略显含糊的对外名字还在，属于已知遗留。

D9 · 排序从三档细化为四档，把「已启用但凭证异常」单独拎出来 v3.0

为什么v3.0 把「已启用」的口径定为只看用户开关 enabled=1（需求四原文：查询「我自己已经启用的连接器」）。而 v2.0 的档 0「可用」= enabled=1 且 status='active'，比用户口径更严格，差异恰好落在「用户启用了、但 token 已过期」这一类上。若沿用三档，这类连接器要么被算进「可用」占住队首（点进去必然 connection_expired，是假绿灯），要么掉到「已连接未启用」里和真正的未启用混作一团（用户会说「我明明启用了，怎么排在没启用的后面」）。两难，所以拆成两档。

实现上不需要写 NOT EXISTS：三个 EXISTS 子查询级联 DESC，三个布尔位恰好切出四种组合。

D10 · 新标注字段叫 connectionEnabled，不叫 enabled v3.0

为什么ProviderDto 里已经有一个含义是「启用」的字段：status（取值 enabled/disabled），指的是连接器目录条目本身由空间管理员设定的启停。再往同一个响应体里塞一个叫 enabled 的字段，两者会在评审、日志、前端代码里反复看混（3.1 的命名陷阱①）。加 connection 前缀直接点明它属于「我的连接」这一维度，与 connected 成对。

代价 名字偏长，且与连接对象上的列名 enabled 不一致（一个是响应字段、一个是数据库列/连接 DTO 字段）。这是刻意的取舍：优先避免同响应体内歧义，两个语境各自自洽。

D11 · 顺带修掉「过滤集合为空时语义反转」的既有缺陷 v3.0

为什么新增的「只看我启用的」过滤天生会遇到「我一个都没启用」这种输入。而 MyBatis-Plus 的 in(condition, …) 在 condition=false 时会整条跳过条件——原代码正是靠「集合非空」当 condition。于是一个连接都没有的用户调 ?connected=connected，拿到的是全量列表而不是空。这是个既有缺陷（v1.0 就在），本次因为要复用同一套机制而一并修掉。

修法是抽出 filterByServices(wrapper, services, include) 统一处理四种组合：正向且集合为空 → 恒假条件 eq(id, -1L)（与 repository 里既有的 visibleWrapper 同法，也避开了 in () 的语法错）；反向且集合为空 → 不拼条件（本来就一条都不该排除）。

代价 无行为代价，但这条没能端到端实测：本地唯一可用的 AK 名下有 8 条连接，构造不出「零连接用户」。该分支是按构造正确（与既有恒假手法一致），验收如需覆盖，请用一个新账号（本地唯一可用的 AK 名下有 9 条连接、覆盖 8 个 service，构造不出「零连接用户」）。

已知限制与待办Known Limits

8.1 两处已知遗留（都不影响本次验收）

① getOwned 不排除 disconnected（v1.0 就存在的防御性小洞）。getOwned 只校验 id + user_id，而 setEnabled 走的正是它。目前到不了这条路径：disconnect 是 DELETE 行（凭证行一起删），disconnected 又是代码不再写入的历史值。但若日后有人把「断开」改成写墓碑值而不是删行，?enabled=true 会把墓碑复活，而 credential_id 指向的凭证行已不存在 → 执行报 credential_not_found。

是否补由验收人定：补法是 setEnabled 里加一行 if (DISCONNECTED.equals(status)) throw CONNECTION_NOT_FOUND;。v2.0 没有补 —— 本次的目标是拆分语义，不是扩大改动面。

② 对外方法 IConnectorApiService.hasActiveConnection 的名字仍未改（D8 的代价）。它的语义是「有没有可执行的连接」（实现已换成 firstExecutable），但名字停留在 active 时代。改名会扩散出 connector 模块，违反「改动不扩散」的约束，故只把模块内部的私有方法正名为 executableServices。

8.2 有意为之、请勿当 bug 报的几条

现象为什么是有意的
启用一条 expired 连接后，它仍然是 expired，执行报 connection_expiredD2：启用只写 enabled。宁可当场说清「去重新授权」，也不给一个会撞墙的假绿灯。这是 v2.0 与 v1.0 行为差别最明显的一条。
停用的连接调动作报 connection_disabled 而不是 connection_requiredD3：两者指向的动作不同，混用会把用户引去重连
既停用又过期时报 connection_disabled（而不是 expired）判断顺序：先解决用户意图（去启用），启用后自然会看到 connection_expired。顺序反了会让用户在两个动作间来回跑
停用的连接仍显示「已连接」需求原文「连接器还是看得到」；也是 D6 的档位依据
控制台卡片上没有启停开关启停是连接维度；能力中心已定调不展示开关
Agent/SDK 侧「已连接」与目录侧「已连接」口径不同SDK 用 firstExecutable（含启用与健康度），目录用 listByUser（含停用）。Agent 侧本就该看到「不可用」。同名字段两种口径确实是个坑，内部方法已借本次正名。
排序不接受参数固定行为；别的口径由客户端二次排序。v3.0 新增的是过滤参数（connectionEnabled），排序本身仍无参数。
?connectionEnabled=true 的结果里包含凭证已过期的连接器 v3.0用户拍板的口径：「已启用」严格只看 enabled=1，不掺 status。凭证健康度是执行时才需要知道的事（connection_expired），不在列表过滤里替用户做决定。见 D9 与验收点 d13。
档 0 与档 1 在返回体里看不出区别 v3.0两者的 connected 与 connectionEnabled 都是 true，差别只在顺序。要精确区分得看连接详情的 status（D9 的代价）。
?connectionEnabled=true 在线上被静默忽略 v3.0testagent 上还没有这个参数，Spring 对未声明的 query param 不报错、直接返回全量。别当成「过滤生效但没数据」—— 见 05 末尾的部署状态。

# 1) 基线：记录 enabled 与 status 两个字段（末尾要逐字复原）

共库警告

本地 dev 的 MySQL 就是 testagent 同一个库。所以验收时请遵守：

  • 用既有连接测，不要新建连接；不要删任何连接。
  • 每条连接测完必须把 enabled 与 status 都还原（见命令 9），并在末尾确认「没有 enabled != true 或 status != 'active' 的残留」。
  • 第 6 步的 status='expired' 是手工制造的，用完必须改回 active —— 留着一条假的过期连接会污染后续测试。
  • 验证执行侧时优先用只读类动作，避免产生真实外部副作用。被拒的调用（disabled/expired）根本不会触达上游，只有「启用且健康」那一次会真实调用。
  • 命令里的 AK 用本地的，不要用生产 AK。
