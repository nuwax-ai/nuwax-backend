# nuwax-agent-scheduler API Reference

端点级契约。使用方式与语义纪律见 [../SKILL.md](../SKILL.md)。
本文件里的每条行为都经**线上实测**（2026-09-26，本地实例 + 真实沙箱 AK 打通全链路）。

- 前缀：`/api/v1/4sandbox/task`（挂在 `PLATFORM_BASE_URL` 下）
- 方法：**全部 POST**，`Content-Type: application/json`
- 鉴权：`Authorization: Bearer <SANDBOX_ACCESS_KEY>`；AK 必须**锚定着某个智能体**
  （沙箱环境里现成的那把就满足）。★租户永远不需要传。
- 响应信封（所有端点一致）：

```json
{ "code": "0000", "displayCode": "0000", "message": "success", "data": ..., "tid": "..." }
```

`code == "0000"` 才是成功；**业务失败也走 HTTP 200**，判据是 `code`。

---

## 可见范围（所有端点共同前提）

服务端按 AK 解析出归属用户与绑定智能体（沙箱 AK 的 `targetId` 形如 `{agentId}-{conversationId}`，
服务端取横杠前的 `agentId`）。四个端点都在这个范围内工作：

- create / list：按「**创建人 = AK 归属用户** + **智能体 = AK 锚定的智能体**」收口。
- update / cancel：只校验「任务存在」+「任务的智能体 == AK 锚定的智能体」，
  **不校验任务是不是当前会话建的、也不校验任务状态**（见 §2/§3）。
- ★**list 不是「当前会话的任务」，是「本用户名下、本智能体的全部定时任务」**——
  实测能看到同一智能体**另一个会话**里创建的任务。反过来，别的智能体、别的用户的任务看不到。

## 1. POST /create —— 创建定时任务

请求体：

```json
{
  "taskName": "每日报表",
  "executeType": "Loop",
  "message": "输出今天的待办清单",
  "conversationId": 1694106,
  "cron": "0 0 9 * * ?",
  "spaceId": 57
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `taskName` | string | **是** | 任务名称 |
| `executeType` | string | **是** | `Once`（一次性）/ `Loop`（循环） |
| `message` | string | **是** | 任务触发时发给智能体的内容。★服务端强制要求：缺了报 `4000`「任务执行内容消息不能为空」；★默认要含「用 nuwax-im 把结果推给用户」的指令，见 [../SKILL.md](../SKILL.md)「★`--message` 里要带…」；★建任务时本次运行若是**群消息触发**（`IM_SCENARIO=group` / 有 `IM_GROUP_CONV_ID`），用 `send-group --conv-id <群会话ID 的具体数字>` **优先发回该群**，要通知某个人就在同一条里 `--mention-user-ids <他的数字ID>`；★群发报 `IM_20104`（执行那次的当前身份不是该群成员）时**回落 `send-p2p` 通知本人**，这条退路要一并写进 `message`（**别静默失败**）；★非 IM 触发时（无群上下文）**按用户要求定**：要求发某个群同样用 `send-group` + 该群 ID，只通知本人才私聊；★`IM_SCENARIO` / `IM_GROUP_CONV_ID` **不是必须的**（任务执行那次可能为空），为空照常发群 —— 见 SKILL.md「★群消息触发时：优先发回该群」 |
| `conversationId` | long（JSON 数字） | **是** | 任务挂靠的会话 ID —— 就是环境变量 `CONVERSATION_ID`。服务端校验它属于 AK 锚定的智能体，否则报「conversationId 错误，请从环境变量中获取」 |
| `lockTime` | string | `Once` 必填 | 执行时间，ISO 8601（脚本收 `YYYY-MM-DD HH:MM:SS` 后自行补时区）。缺了报 `4000`「执行时间不能为空」 |
| `cron` | string | `Loop` 必填 | **Quartz 6 字段**，见 §5。缺了报 `4000`「定时cron表达式不能为空」 |
| `spaceId` | long（JSON 数字） | 否 | 任务归属的空间ID。**传入后服务端只校验「当前用户是否为该空间成员」（`space_user` 有行即通过，不限空间类型），不校验智能体所在空间**；不是成员报「没有指定空间的权限，无法在该空间创建定时任务」。不传则回落到用户个人空间。对应脚本 `--space-id` |

★**空间归属语义（服务端 `TaskCenterForSandboxController#create`）**：
- 传 `spaceId`：成员校验用 `querySpaceUser(spaceId, userId)`——直查 `space_user` 行，**不看空间类型**，所以 Personal / Team / Group / DM 空间只要用户是成员都能指定。**别改用 `queryListByUserId`**：它当前委托 `queryVisibleListByUserId`，类型白名单只含 Personal/Team，会把 Group/DM 漏掉造成误拒（接口 Javadoc 声称含 DM/Group，与实现不符）。
- 不传 `spaceId`：沿用既有回落——尝试智能体发布空间，最终落到用户个人空间；无个人空间报「用户缺少个人空间数据，无法创建当前任务」。

响应 `data`：

```json
{ "id": 4640 }
```

| 字段 | 说明 |
|---|---|
| `id` | 新建任务的 ID（正整数），后续 update / cancel 用它 |

★**`id` 必须自己看**：`cron` 只有服务端认得才算数。服务端现在会明确拒绝
（`0001 任务创建失败，请检查 cron 表达式（需 Quartz 6 字段）后重试`）；历史行为是回
「成功 + `id=0`」而任务其实没建 —— 所以**拿不到正整数 `id` 就是没建成**，别只看信封的 `code`。

## 2. POST /update —— 更新定时任务

请求体：

```json
{ "id": 4640, "taskName": "新名字", "message": "改后的内容" }
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | long | **是** | 任务 ID |
| `taskName` | string | **是** | 任务名称（每次都要带上，不是「不改就不传」） |
| `executeType` | string | 否 | 传了就要按类型补参数：`Once` 必须带 `lockTime`，`Loop` 必须带 `cron` |
| `lockTime` | string | 否 | 一次性任务的执行时间 |
| `cron` | string | 否 | 循环任务的 cron（Quartz 6 字段） |
| `message` | string | 否 | ★**只有非空白才覆盖**；不传 = 保持原内容（不清空）。★群任务的推送写法要改也走这个字段（`send-group` + 群会话 ID 数字，要通知谁再加 `--mention-user-ids` + 数字，并带上「报 `IM_20104` 就回落私聊」的退路）；非 IM 触发时按用户要求定（要发某个群同样用 `send-group` + 该群 ID，只通知本人才私聊） |

响应 `data` 为 `null`，看 `code`。

★语义纪律（实测）：
- **不校验状态**：已取消、已跑完的任务照样能改（只要 ID 对、智能体对）。
- **不校验会话**：任务不是当前会话建的也能改（见「可见范围」）。

### ★★ 这个端点改不动「周期」（实测 + 代码双向确认）

`executeType` 那段分支**只有 `Once` 一侧真正落库**：

| 传了什么 | 实际结果 |
|---|---|
| `executeType=Loop` + `cron` | 校验 `cron` 非空 → **丢弃 cron**。周期原封不动，接口回成功 |
| `executeType=Once` + `lockTime` | `cron` 被写成 `toCron(lockTime)`（秒/分/时/日/月，**无年份**），并由此重算 `lockTime` |
| 不传 `executeType` | 整段跳过，只改 `taskName` / `message` |

两条独立的证据：① 端到端实测——对一个循环任务传入新 `cron` 后，`/list` 返回的 `cron` 与
`lockTime` 均未变化，而 HTTP 层回的是成功；② 服务端 `TaskCenterForSandboxController#update`
的 `Loop` 分支只写了 `maxExecTimes`，**没有 `setCron`**；且 `ScheduleTaskApplicationServiceImpl#updateById`
会把 `maxExecTimes` 显式置空，所以那一侧连类型都改不动。

推论（调用方需要知道的就这两条）：
- **想改周期只能重建**：`cancel` 旧任务 + `create` 新任务（新 ID）。别用 update 的「成功」当改成了。
- **`lockTime` 的年份会被丢掉**：`Once` 的周期只有「日/月」粒度，实际执行时刻是
  `getNextExecDate(cron)` 算出的**下一次发生**。传 `2028-01-01 10:00:00` 落到 `2027-01-01 10:00`。

> ⚠️ 这是服务端当前行为的记录，不是技能侧的限制——技能脚本照原样发请求，不做本地拦截
> （唯一例外：同时给 `--cron` 和 `--lock-time` 又不说类型时，脚本会报错要求显式指定）。

## 3. POST /cancel/{id} —— 取消定时任务

★**id 在路径上**，不是请求体：

```
POST /api/v1/4sandbox/task/cancel/4640
```

响应 `data` 为 `null`，看 `code`。

★语义纪律（实测）：
- **幂等**：对同一个任务重复调用**都回成功**（与 nuwax-agent-task 的 `/cancel` 不同 ——
  那边回 `cancelled=false` 表示「什么都没变」，**本端点没有这个字段**，别把两套语义混着读）。
- **不校验状态**：对已完成 / 已取消的任务调用同样回成功，并把状态改写成 `CANCEL`。
- **取消后该任务立刻从 `/list` 消失**（§4 的状态过滤把 `CANCEL` 排除了）——
  所以「取消成功但列表里找不到」是正常的，不代表没取消。
- ⛔ 取消后**没有「恢复」**：要重新起一个，只能重新 `create`（那是新任务、新 ID）。

## 4. POST /list —— 查询定时任务列表

请求体：无（脚本不发 body）。

响应 `data`：任务数组（按 ID 倒序 = 最近创建在前）。

```json
[
  {
    "id": 4641,
    "taskName": "调试-每日9点",
    "executeType": "Loop",
    "conversationId": 1694106,
    "cron": "0 0 9 * * ?",
    "message": "输出今天的待办清单",
    "lockTime": "2026-09-27T01:00:00.000+00:00"
  }
]
```

| 字段 | 说明 |
|---|---|
| `id` | 任务 ID，update / cancel 用 |
| `taskName` | 任务名称 |
| `executeType` | `Once` / `Loop`。★**不是存下来的字段**，服务端按「最大执行次数 == 1」反推 |
| `conversationId` | 任务挂靠的会话 ID（可能**不是**当前会话，见「可见范围」） |
| `cron` | 该任务的执行 cron。★**`Once` 任务也有**（服务端把执行时间转成了 cron 存下来，如 `0 0 10 1 1 ?`） |
| `lockTime` | ★**下次执行时间**，`Once` 与 `Loop` **都可能有**。`Loop` 上它是服务端算出的下一次触发时刻，别当成「只给一次性任务用」 |
| `message` | 任务触发时发给智能体的内容 |

★**只回「未完结」的任务**：服务端状态过滤为 `CREATE / CONTINUE / EXECUTING / FAIL`，
**已跑完（`COMPLETE`）、已取消（`CANCEL`）、超次（`OVERFLOW_MAX_EXEC_TIMES`）一律不出现**
（实测：取消后立刻从列表消失）。所以：

- 列表为空 = **没有待执行的定时任务**，不代表「从来没建过」；
- 跑了的一次性任务会自己从列表消失，这是预期行为，不是被删了；
- ⛔ 别拿列表判断「某事做过没有」——它只是**待执行队列**。

★**时间是 UTC**：`2026-09-27T01:00:00.000+00:00` 是北京时间 `2026-09-27 09:00`。
给使用者报时间时要转成当地时间。

★小坑：任务 params 里没有 message 时（非本技能创建的老数据），`message` 会是字符串 `"null"`。

## 5. cron 格式（★最容易写错的地方）

平台用 **Quartz** 解析 cron，必须是 **6 字段**（可 7 字段带年），**不是 Linux crontab 的 5 字段**：

```
秒  分  时  日  月  周
0   0   9   *   *   ?
```

★硬规则：**「日」与「周」两个字段必须有且只有一个写 `?`**（Quartz 不允许同时指定两者）。

| 想要的周期 | 正确写法（Quartz 6 字段） | ⛔ 常见错写（5 字段 crontab） |
|---|---|---|
| 每天 9:00 | `0 0 9 * * ?` | `0 9 * * *` |
| 每 5 分钟 | `0 */5 * * * ?` | `*/5 * * * *` |
| 每 2 小时 | `0 0 */2 * * ?` | `0 */2 * * *` |
| 周一到周五 9:00 | `0 0 9 ? * 1-5` | `0 9 * * 1-5` |
| 每月 1 号 0:00 | `0 0 0 1 * ?` | `0 0 1 * *` |

技能脚本会**在本地先校验**这个格式，不合规直接以退出码 1 拒绝、不发请求 ——
因为写错的代价极隐蔽：服务端不接受这个表达式时，**信封仍是成功、只有 `data.id` 是 `0`**，
任务根本没建（脚本已代判，非正整数一律报失败）。

★时区：平台按**服务端 JVM 时区**把 cron 落地成执行时刻。脚本默认按 `+08:00` 解析
`--lock-time`（与线上服务端一致，实测请求的 `2027-01-01 10:00:00` 原样回读为同一时刻）。
服务端时区不是 +08:00 时才需要设 `TASK_TIMEZONE_OFFSET`。

## 错误码

`code` 只有三档（实测）：

| code | 场景 | 已实测的例子 |
|---|---|---|
| `0000` | 成功（`data` 里的 `id` 要自己看，见 §5） | 四个端点的正常路径 |
| `0001` | **业务拒绝** —— 参数语义不对 / 目标不可见 | `conversationId 错误，请从环境变量中获取`；`任务不存在`；`Invalid task id`；`Agent不存在或已下架`；`用户缺少个人空间数据，无法创建当前任务`；`你能创建的任务数量已达上限…`；`任务创建失败，请检查 cron 表达式（需 Quartz 6 字段）后重试` |
| `4000` | **参数硬校验失败 / 服务端异常** | `任务执行内容消息不能为空`；`执行时间不能为空`；`定时cron表达式不能为空`；内部异常（如 AK 形态解不出智能体，回 `Failed to convert value of type 'java.lang.String'…` 这类原始异常文案） |

★两档的**处理方式不同**：`0001` 是「你的请求语义不对，改参数或用别的任务 ID」；
`4000` 是「请求本身缺字段/服务端没接住」，**message 是原始异常文案时不要直接转述给使用者**，
按 message 补齐参数或报「服务暂时不可用」；`message` 是 `xxx不能为空` 时按字面补参数。

## 明确不存在的能力

- **无单任务查询**：只有 `/list`，没有 `GET /{id}`。要某条任务的信息就从 list 里挑。
- **无删除**：只有「取消」（改状态），没有物理删除。终态任务由平台按时间自动清理。
- **无恢复**：取消不可逆，要重来只能重新 `create`。
- **无「立刻执行一次」**：`Once` 任务的 `lockTime` 必须是未来时间，没有「马上跑」的参数。
- **无跨智能体/跨用户可见**：范围恒为「本 AK 智能体 + 本用户名下」（见「可见范围」）。
- **无执行历史/结果**：本端点家族只管**调度**，既不回传任务执行结果、也不代投 ——
  默认由那次运行**自己**用 nuwax-im 把结果推给用户（靠 `message` 承载）；
  **群消息触发时建的任务则优先发回那个群**（`send-group`；报 `IM_20104` 时回落 `send-p2p`
  通知本人，别静默失败），见
  [../SKILL.md](../SKILL.md)「★群消息触发时：优先发回该群」；要查执行过程才用
  nuwax-agent-task 技能的 `progress`。
