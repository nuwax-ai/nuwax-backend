# Nuwax 定时任务（Agent Scheduler）

## Overview

管理「到点自动让智能体做事」的定时任务。支持一次性任务（Once，指定某个时刻执行一次）和
循环任务（Loop，用 cron 定义周期）。任务到点时，平台会把任务里带的**消息内容**投给智能体执行。

**何时使用：** 用户表达「定时 / 延迟 / 周期性地做某件事」的意图时，例如「明天 9 点提醒我开会」、
「每天早上发日报」、「每 5 分钟检查一次状态」、「查看 / 取消我之前设的提醒」。

★**用户说的是「自动化」时也算**：「把这个自动化」「让它以后自动跑」「每天自动帮我做 XX」
——这是在要一个「到点自动执行」的定时任务，走本技能。别因为对方没说「定时任务」四个字就漏掉：
「自动化」与「定时 / 到点自动执行」在本平台是同一件事（不存在独立的「自动化流程编排」能力）。

**何时不使用：** 运行环境缺少 `PLATFORM_BASE_URL`、`CONVERSATION_ID`、`SANDBOX_ACCESS_KEY`
任一环境变量时，脚本无法工作，不要调用。

以下命令均在技能根目录下运行。四个能力收在**同一个脚本** `scripts/scheduler.py` 里，
用子命令区分：`python3 scripts/scheduler.py <create|update|cancel|list>`（公共逻辑已并入该文件）。

## Environment Variables

| 变量名 | 说明 |
|--------|------|
| `PLATFORM_BASE_URL` | 平台接口根地址 |
| `CONVERSATION_ID` | 当前会话 ID，创建任务时用（也用于校验调用方身份） |
| `SANDBOX_ACCESS_KEY` | 沙盒与平台通信密钥，脚本自动拼 `Authorization` 头 |
| `IM_SCENARIO` | **只读、不是必须的**：触发场景，`group`（群消息）/ `p2p`（私聊）。非 IM 触发时不存在；**任务到点执行那次可能为空** |
| `IM_GROUP_CONV_ID` | **只读、不是必须的**：群消息触发时的**群会话 ID**。私聊 / 非 IM 触发时不存在；**任务到点执行那次可能为空** |
| `IM_CONV_ID` | **只读、不是必须的**：本次触发的会话 ID（群、私聊都有） |

★★**三个 `IM_*` 变量都不是必须的 —— 没有它们照样能建任务、照样能发群**：
它们只在**群里那次对话运行**里可能有值；**任务到点执行那次也可能为空**。
所以别把「变量是空的」当成「发不了群」：群会话 ID 与被 @ 的 userId 一律**从对话里抄成数字写进 `--message`**，
发不发群只看用户的要求（见下节），跟这几个变量有没有值无关。

## ★先记住这六条语义

1. **cron 是 Quartz 6 字段，不是 Linux crontab 的 5 字段**——见下节。写错会被脚本本地拦下。
2. **`--message` 是必填**：任务到点时发给智能体的内容。没有它任务存在也没有意义。
3. **列表只含「待执行」的任务**：已跑完（一次性任务执行过）、已取消的任务会自己消失。
   所以「列表为空」= 没有待执行的定时任务，**不代表从来没建过**；
   也**别拿列表判断某事做过没有**。
4. **列表不是「当前会话的任务」**：范围是「本用户名下、本智能体的全部定时任务」，
   会看到同一智能体**别的会话**里建的任务。
5. **时间字段是 UTC**：如 `2026-09-27T01:00:00.000+00:00` 是北京时间 `2026-09-27 09:00`。
   转述给使用者前要先转成当地时间。
6. **执行结果默认要推给用户，推回哪儿看场景 + 用户要求**：`--message` 里要写明
   「执行完把结果用 nuwax-im 发给用户」—— 任务到点时用户不在对话里，结果只落在会话里他看不到。
   **群消息触发时建的，优先发回那个群**（`send-group` + 群会话 ID）；有人要求「通知我」也在群里 @ 他，
   并把「群发报 `IM_20104` 就回落私聊」的退路一并写进去（见下节）。
   **没有群上下文时**（网页对话等）不默认私聊 —— 用户要求发到某个群就 `send-group`，只要求通知本人
   才 `send-p2p`。★**`IM_*` 环境变量不是必须的**：没有它们（任务执行那次可能为空）也一样，
   发群要靠 `--message` 里写死的群会话 ID 数字，不靠变量。见下节。

另：**取消不可逆**，没有「恢复」；要重来只能重新创建（那是新任务、新 ID）。

## ★`--message` 里要带「把结果推给用户」

**任务到点时用户不在对话里** —— 执行结果只留在会话里，他不会主动去翻。
所以 `--message` 默认要写明：**执行完用 nuwax-im 把结果私聊发给用户**。

`--message` 的三段结构：

| 段 | 写什么 |
|---|---|
| 干什么 | 用户要的事（查天气 / 生成日报 / 检查服务状态…） |
| 推给谁 | **群消息触发时：优先发回那个群** `send-group --conv-id <群会话ID>`，要通知某个人就在群里 @ 他；群发报 `IM_20104` 时回落私聊 `send-p2p --to-user-id <本人的数字>`；<br>**没有群上下文时按用户要求**：要发某个群就 `send-group --conv-id <该群会话ID>`，只通知本人则私聊 `send-p2p --to-user-id "$SYS_USER_ID"`（见下节） |
| 推什么 | 结果正文本身 —— **不是**「已完成」「任务执行完毕」这类空话 |

```bash
python3 scripts/scheduler.py create \
  --task-name "每日天气播报" \
  --execute-type Loop \
  --cron "0 0 9 * * ?" \
  --message '查询成都今天的天气，整理成 3 行以内的中文播报，然后用 nuwax-im 技能私聊发给用户：python3 scripts/im.py send-p2p --to-user-id "$SYS_USER_ID" --text "<播报正文>"'
```

- 例子里的 `scripts/im.py` 是 **nuwax-im 技能**的入口脚本（**不是**本技能的 `scheduler.py`）——
  上面那段是写进 `--message` 给执行时那次运行读的指令。
- **收件人用 `$SYS_USER_ID`**（沙箱环境变量 = 本次运行的用户 ID），别写死 ID。
  整个 `--message` 用**单引号**包裹，让 `$SYS_USER_ID` 到任务执行时才展开。
- **为什么必须写进 `--message`**：任务触发的那次运行**只拿到这段文字**，
  看不到你建任务时的对话 —— 不写进去，到点就不会推。
- **用户说了「不用推 / 我自己看」**时才省略这一段。
- 推送报 `4030` 时，可改用 `system-notify --to-user-ids "$SYS_USER_ID"`（仅管理员，
  收件方看到的是「系统通知」）。★但若 `IM_SCENARIO=group`（本次是群消息触发的），
  **按下一节优先发回群里**（要通知谁就在群里 @ 他）；只有群发报 `IM_20104` 时才回落私聊。

## ★群消息触发时：优先发回该群，要通知谁就在群里 @ 他

**先判断这是不是群场景** —— 环境变量有就看，**没有也不影响写法**（它们不是必须的，见上文）：

| 参考 | 场景 | 推送怎么写 |
|---|---|---|
| `IM_SCENARIO=group`（或存在 `IM_GROUP_CONV_ID`） | **群消息触发** | 优先 `send-group --conv-id <该群会话 ID 的具体数字>`；群发报 `IM_20104` 时回落 `send-p2p --to-user-id <本人的数字>` |
| `IM_SCENARIO=p2p` | 私聊触发 | 私聊 `send-p2p --to-user-id "$SYS_USER_ID"` |
| 三个变量都不存在（网页对话等；**任务到点执行那次可能为空**） | 非 IM 触发 | **看提示词本身的要求**：要求结果进某个群就 `send-group --conv-id <该群会话ID 的数字>`；只是通知本人则私聊 `send-p2p --to-user-id "$SYS_USER_ID"` |

★**第三行不是「默认私聊」，也不是「发不了群」**：非 IM 触发时没有群上下文可看，发到哪儿**完全由用户的要求（= 写进 `--message` 的提示词）决定**。
用户说「结果发到 XX 群 / 群里同步一下」，就写 `send-group` + **那个群的会话 ID（数字）**；
只有用户要的是「通知我」而没提群，才写私聊。别因为「环境变量里没有群信息」就默认走私聊——那是两回事。

★**变量为空是正常的**：`IM_SCENARIO` / `IM_GROUP_CONV_ID` 只在群里那次对话运行里必然有值，
**任务到点执行那次可能为空**。所以不要把「这两个变量是空的」当成问题、也不要指望靠它们判断——
**写进 `--message` 的群会话 ID 数字**才是唯一可靠的东西，它是给执行时那次运行用的。

★判据**不看** `IS_GROUP_MESSAGE`（那是上游写入的布尔值，可被伪造）；平台侧同样只用
「`IM_SCENARIO=group` 或群会话键在不在」，两边口径一致。

**群消息触发时建的任务，优先用 `send-group` 发回同一个群会话 ID**：
结果只发成私聊的话，群里没人看得到。

★**唯一的例外 —— 群发报 `IM_20104`**（执行那次的当前身份不是该群成员）：
这时**回落 `send-p2p` 通知本人**。这条退路必须**写进 `--message`**——
群发失败就静默结束是最糟的结果：任务看着「跑了」，用户什么都没收到。

群场景下 `--message` 里要写全这几件事：**发到群里**、**群会话 ID 的具体数字**、用 **`send-group`**，
以及**群发失败时改私聊通知本人**。

```bash
python3 scripts/scheduler.py create \
  --task-name "每日天气播报" \
  --execute-type Loop \
  --cron "0 0 9 * * ?" \
  --message '查询成都今天的天气，整理成 3 行以内的中文播报，然后发到群里：python3 scripts/im.py send-group --conv-id 227009028956360704 --text "<播报正文>"；若这步报 IM_20104（当前身份不是该群成员），改用私聊通知本人：python3 scripts/im.py send-p2p --to-user-id "$SYS_USER_ID" --text "<播报正文>"，不要静默结束'
```

★★**群会话 ID 必须写死成数字，不能写 `$IM_GROUP_CONV_ID`**：任务到点那次执行时这些
`IM_*` 变量**可能为空**（IM 上下文由群对话那次运行留下，任务那次不一定带着），
写变量会在执行时展开成空串，等于给了一条没有目标的命令。**这个 ID 只能靠 `--message` 这段文字带过去。**

### 要把结果通知给某个具体的人 → 在群里 @ 他

群里有人说「结果通知我 / 提醒我」时，**仍然发回那个群，在同一条消息里 @ 他** ——
「要通知某个人」不是退化成私聊的理由（只有群发报 `IM_20104` 时才回落私聊）：

```bash
--message '查询成都今天的天气，整理成 3 行以内的中文播报，然后发到群里并 @ 他：python3 scripts/im.py send-group --conv-id 227009028956360704 --mention-user-ids 366 --text "<播报正文>"；若这步报 IM_20104，改用私聊通知本人：python3 scripts/im.py send-p2p --to-user-id "$SYS_USER_ID" --text "<播报正文>"，不要静默结束'
```

- `--mention-user-ids <userId>`（多人用逗号分隔）或 `--mention-all`（@ 全体）。
- ★**被 @ 的 userId 同样只能写成数字**：要 @ 谁就把他的 userId 抄成数字写进 `--message` ——
  本次群消息触发时，说话的那个人就是 `IM_SENDER_ID` 的值，直接抄那个数字（任务执行时没有
  `IM_SENDER_ID`，写 `$IM_SENDER_ID` 会 @ 到空）。
- 只 @ 少数人时**不要用 `--mention-all`**（会打扰整群）。

★**建完自己核一遍**：`scheduler.py list` 里该任务的「消息内容」应当能直接看到
`send-group` 和那串群会话 ID（要 @ 人还应有 `--mention-user-ids` 和数字）。看不到就说明没记进去，
`update` 改 message 重写。

★写成私聊**照样能发出去**，没有错给你看 —— 只是群里没人看得到。**别指望报错提醒你，靠上面几条自己写对。**
★反过来，**群发失败必须有人知道**：`send-group` 报 `IM_20104` 时按退路回落私聊，**绝不静默结束**。

> 待实测：任务到点执行时用的身份与建任务时是否一致（能否发进该群、@ 是否生效）尚未在真机跑过。
> 若 `send-group` 报 `4030` / `IM_20104`，**如实报告，不要改成 `send-p2p` 硬发**
> （那是把「发不进群」伪装成「发出去了」，群里照样看不到）。

群场景下 `scheduler.py` 会自己检查 `--message` 有没有写全上面几件事，缺了就打印
`⚠️ 群场景提醒`——**只提醒、不阻断**（用户明说「不用推」时照样要能建任务）。

## Workflow

按用户请求的操作类型执行对应命令。

### 1. 创建定时任务

**一次性任务（Once）：**
```bash
python3 scripts/scheduler.py create --task-name "任务名称" --execute-type Once --lock-time "2026-09-01 09:00:00" --message '要做什么 ＋ 用 nuwax-im 把结果推给用户（见上节）'
```

**循环任务（Loop）：**
```bash
python3 scripts/scheduler.py create --task-name "任务名称" --execute-type Loop --cron "0 0 9 * * ?" --message '要做什么 ＋ 用 nuwax-im 把结果推给用户（见上节）'
```

| 参数 | 必填 | 说明 |
|------|------|------|
| `--task-name` | 是 | 任务名称 |
| `--execute-type` | 是 | `Once`（一次性）/ `Loop`（循环） |
| `--message` | **是** | 任务触发时发给智能体的内容。★默认要含「用 nuwax-im 把结果推给用户」的指令；**本次是群消息触发时改为优先发回群里**（`send-group` + 群会话 ID 的数字，要通知谁就加 `--mention-user-ids`，再补一句「报 `IM_20104` 就回落私聊」）——两节都在上面 |
| `--lock-time` | 仅 Once | 执行时间，格式 `YYYY-MM-DD HH:MM:SS`，必须是未来时间 |
| `--cron` | 仅 Loop | **Quartz 6 字段** cron 表达式，见下节 |
| `--space-id` | 否 | 指定任务归属的空间ID。传入后服务端**只校验当前用户是否为该空间成员**，不校验智能体所在空间；无权限报「没有指定空间的权限，无法在该空间创建定时任务」。不传则回落到用户个人空间 |

★成功的判据是**看到正的「任务ID」**（如 `🆔 任务ID: 4640`）。历史上有过「回成功但任务没建」的
静默失败，脚本现在会把「没拿到任务 ID」判为失败（退出码 1），照它的结论走。

### 2. 更新定时任务

```bash
python3 scripts/scheduler.py update --task-id <任务ID> --task-name "新任务名称" [--message "..."]
```

| 参数 | 必填 | 说明 |
|------|------|------|
| `--task-id` | 是 | 任务 ID |
| `--task-name` | 是 | 任务名称（**每次都要带**，不是「不改就不传」） |
| `--message` | 否 | 传了才覆盖；不传 = 保持原内容（不会清空）。★改群任务的推送写法也走这里，别忘了 `send-group` + 群会话 ID 的数字（见上节） |
| `--execute-type` | 否 | `Once` / `Loop`；不传时脚本按「给了 `--cron` 就 Loop、给了 `--lock-time` 就 Once」自动判定（两个都给则报错，需显式指定） |
| `--lock-time` | 否 | 一次性任务的执行时间，格式 `YYYY-MM-DD HH:MM:SS` |
| `--cron` | 否 | 循环任务的 Quartz 6 字段 cron |

★★**这个接口实际上改不动「周期」，只会回成功**（实测 + 服务端代码双向确认，见
[references/api_reference.md](references/api_reference.md) §2）：

- **`--execute-type Loop --cron ...`：周期原样不动**。服务端只校验 `cron` 非空，然后**把它丢掉**，
  接口照样回成功——「把一次性改成每天 9 点」「把每天改成每小时」目前都做不到。
- **`--execute-type Once --lock-time ...`：会写周期**，但写进去的是「该时刻的 日/月 粒度」表达式，
  ★**年份会被丢掉**（传 `2028-01-01 10:00:00`，实际执行时间会落在 `2027-01-01 10:00`）。
- **`--execute-type` 本身也不改变任务类型**：`Once`/`Loop` 是服务端拿「最大执行次数」反推的，
  而这个字段在更新时被忽略。

所以 update 真正可靠能改的只有**任务名**和**消息**。★**要换周期，就 `cancel` 掉旧任务、
按新周期 `create` 一个新的**（新任务、新 ID）——别用 update 改周期，更别把它的「成功」当作改成了。

### 3. 取消定时任务

```bash
python3 scripts/scheduler.py cancel --task-id <任务ID>
```

| 参数 | 必填 | 说明 |
|------|------|------|
| `--task-id` | 是 | 要取消的任务 ID |

★取消是**幂等**的：重复取消同一个任务都会回成功，**没有**「其实没变」这种信号
（不同于 nuwax-agent-task 的取消会回 `cancelled=false`，别把两套混着读）。
取消后该任务立刻从列表消失，这是正常的。

### 4. 查询定时任务列表

```bash
python3 scripts/scheduler.py list [--json]
```

| 参数 | 必填 | 说明 |
|------|------|------|
| `--json` | 否 | 以 JSON 格式输出 |

★列表只含待执行的任务（见「★先记住这六条语义」第 3 条）；
每条都带 `执行时间`（= **下一次执行时刻**）与 `执行周期`（一次性任务也有等价 cron），
**判断类型只看「执行类型」那一行**。

## Scripts

技能只有**一个**脚本，四个子命令各对应一个能力（公共逻辑内联在同一文件里）：

| 子命令 | 功能 |
|------|------|
| `scripts/scheduler.py create` | 创建一次性 / 循环任务 |
| `scripts/scheduler.py update` | 更新任务（可靠可改：任务名、消息） |
| `scripts/scheduler.py cancel` | 取消任务 |
| `scripts/scheduler.py list` | 查询任务列表（只含待执行） |

`python3 scripts/scheduler.py --help` 看全部子命令，`python3 scripts/scheduler.py <子命令> --help` 看该子命令的参数。

成功输出示例（创建）：
```
✅ 定时任务创建成功!
🆔 任务ID: 4640
📋 跟踪ID: trace-id-123
```

## Cron Expression Format

平台用 **Quartz** 解析 cron，必须是 **6 字段**（`秒 分 时 日 月 周`），**不是** crontab 的 5 字段：

```
秒  分  时  日  月  周
0   0   9   *   *   ?
```

★硬规则：**「日」与「周」两个字段，必须有且只有一个写 `?`**。

| 想要的周期 | 正确写法（Quartz 6 字段） | ⛔ 别写成（5 字段 crontab） |
|--------|------|------|
| 每天 9 点执行 | `0 0 9 * * ?` | `0 9 * * *` |
| 每 5 分钟执行 | `0 */5 * * * ?` | `*/5 * * * *` |
| 每 2 小时执行 | `0 0 */2 * * ?` | `0 */2 * * *` |
| 周一到周五 9 点执行 | `0 0 9 ? * 1-5` | `0 9 * * 1-5` |
| 每月 1 号 0 点执行 | `0 0 0 1 * ?` | `0 0 1 * *` |

脚本会**在本地先校验**这个格式：字段数不是 6/7 个，或「日」「周」的 `?` 不是恰好一个，
会**直接以退出码 1 拒绝、不发请求**。收到这种报错就按上表改写 cron，别原样重试。

## Common Issues

- **环境变量未设置**：脚本报 `Missing required environment variables`，补齐
  `PLATFORM_BASE_URL` / `CONVERSATION_ID` / `SANDBOX_ACCESS_KEY` 后重试。
- **认证错误 / 权限不对**：确认 `SANDBOX_ACCESS_KEY` 有效未过期，且它绑定着某个智能体、
  与当前会话是同一个智能体。
- **参数错误**：一次性任务必须给 `--lock-time`；循环任务必须给 `--cron`；创建时必须有 `--message`；
  `--lock-time` 必须是未来时间。
- **`conversationId 错误`**：脚本用的 `CONVERSATION_ID` 不属于当前 AK 绑定的智能体。
  这个值由环境注入，正常不该错；真遇到就 stop 并如实报告，别自己编一个会话 ID。
- **创建报「未返回任务ID」**：任务没建成（最常见是 cron 不是 Quartz 6 字段）。按提示改写后重试。
- **`任务不存在` / `Invalid task id`**：任务 ID 不存在，或该任务不属于当前智能体。
  先跑 `scheduler.py list` 拿一个真实的 ID —— 但注意列表里**没有**已取消/已跑完的任务，
  记忆里的老 ID 可能已经终结，**别硬用**。
- **`update` 回了成功，但周期没变**：这是当前接口的真实行为，不是脚本没生效
  （见 §2 的 ★★）。要换周期就 `cancel` + `create`，别反复重试 update。
- **取消后列表里找不到**：正常（列表只含待执行的任务）。
- **用户说「任务跑了但我没收到推送」**：那次运行里的推送步骤没成功。查 `send-p2p` 的退出码
  （`3`/`3613` 可重试、`4`/`3614` 改参数、`4030` 按上节换 `system-notify`）；
  结果不一定丢，可去该任务挂靠的会话里取。★若任务是群里建的，优先发回群里
  （只有群发报 `IM_20104` 才算回落私聊），别用私聊方式去找原因，先按下面一条核 `--message`。
- **`IM_SCENARIO` / `IM_GROUP_CONV_ID` 是空的，是不是发不了群**：**不是**。这两个变量
  **不是必须的**，且**任务到点执行那次可能为空**（IM 上下文由群对话那次运行留下，任务那次不一定带着）。
  群发靠的是 `--message` 里**写死的群会话 ID 数字** + `send-group`，跟变量有没有值无关 ——
  变量为空时**照常按用户要求发群**，别因此降级成私聊或干脆不推。
- **群任务的推送没发到群里**：建任务时 `--message` 里没写「发回群」——
  群消息触发时不能沿用那套私聊写法。用 `scheduler.py list` 看该任务的「消息内容」里
  有没有 `send-group` 和**群会话 ID 的数字**；★写 `$IM_GROUP_CONV_ID` 同样不行（任务执行时
  该变量可能为空，会展开成空串）；要通知某个人还应有 `--mention-user-ids` + 数字。
  改法：`update --task-id <ID> --task-name "<原名>" --message '<带 send-group 与群会话 ID 的内容>'`。
- **群发报 `IM_20104`（当前身份不是该群成员）**：不是参数写错，而是执行那次没带上该群身份。
  这属于**可预期**的失败，退路要事先写在 `--message` 里：**回落 `send-p2p` 通知本人**，
  别让任务静默结束（群里、私聊都收不到，使用者只会看到「任务跑了但没消息」）。
- **时区**：脚本默认按 `+08:00` 解析 `--lock-time`；服务端时区不是 `+08:00` 时才需要设
  `TASK_TIMEZONE_OFFSET`。列表返回的时间是 UTC（见上文语义第 5 条）。
